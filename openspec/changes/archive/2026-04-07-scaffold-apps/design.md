## Context

Greenfield scaffold of the full job-seeker monorepo. The repository currently contains only documentation (`docs/architecture.md`), tooling config (ESLint, Prettier, EditorConfig), and OpenSpec config. No application code exists. This design covers the structural and architectural decisions for creating all application code.

## Goals / Non-Goals

**Goals:**
- Scaffold a working Yarn 4 monorepo with `apps/api`, `apps/web`, and `packages/shared`
- Implement all 10 NestJS modules with proper wiring (entities, queues, controllers, services)
- Implement the Nuxt 3 admin UI with all four defined pages
- Wire Docker Compose for local development
- Produce runnable stubs — code compiles and starts, core happy paths work

**Non-Goals:**
- Production-hardened error handling beyond basic Bull retry config
- Full test coverage (unit/e2e tests are not part of this scaffold)
- CI/CD pipeline configuration
- Kubernetes manifests (out of scope for initial scaffold)
- OAuth or social login (email+password only)

## Decisions

### NestJS compiler: SWC via nest-cli.json builder
`nest-cli.json` sets `"builder": "swc"`. Requires `@swc/cli` and `@swc/core` as dev dependencies and a `.swcrc` with `experimentalDecorators: true` and `emitDecoratorMetadata: true`. Both `nest build` and `nest start --watch` use SWC — no `tsc` in the hot path.

**Alternative considered:** default `tsc` — rejected; SWC is significantly faster and the test suite (Vitest) also uses SWC, so keeping the same compiler everywhere avoids divergence.

### Monorepo tooling: Yarn 4 workspaces
Yarn 4 is already configured (`.yarnrc.yml` present). Workspaces declared in root `package.json` for `apps/*` and `packages/*`. Avoids hoisting surprises; each app has its own `node_modules` symlinks via PnP or classic node-modules linker.

**Alternative considered:** pnpm workspaces — rejected; Yarn 4 is already set up.

### NestJS module boundaries follow architecture.md exactly
One NestJS module per domain (Auth, Cv, Preferences, JobSources, Ingestion, Matching, Generation, Document, Notification, Applications). Each module owns its entities, service, controller, and queue processor. Cross-module communication only via Bull queues or injected services, not direct repository access across modules.

**Alternative considered:** single monolithic service module — rejected; queue isolation is a key design goal (failures don't cascade).

### ORM: MikroORM with PostgreSQL driver
`@mikro-orm/nestjs`, `@mikro-orm/postgresql`, `@mikro-orm/migrations`. Entity-first approach (decorators). Migrations generated from entity schema.

**Alternative considered:** TypeORM — rejected per architecture doc; MikroORM is specified.

### Queue: Bull with `@nestjs/bull`
One named Bull queue per pipeline stage: `ingestion`, `matching`, `generation`, `document`, `notification`. Each processor is a `@Processor` class in its owning module. Retry config: 3 attempts, exponential backoff.

### LLM: Vercel AI SDK `generateObject` with Claude Haiku
Model: `claude-haiku-4-5-20251001`. Matching and generation both use `generateObject` with Zod schemas. Language instruction injected into every prompt based on `JobSource.language` → `JobPreferences.defaultLanguage` fallback.

### API: JSON:API via `@klerick/nestjs-json-api`
All resource endpoints follow JSON:API spec. The library handles serialization, relationships, and sparse fieldsets. Custom endpoints (login, trigger ingestion manually) are plain REST outside JSON:API.

### PDF: Gotenberg HTTP sidecar, not Puppeteer
PDFs are generated by POSTing rendered HTML to a Gotenberg container (`gotenberg/gotenberg:8`) at `$GOTENBERG_URL/forms/chromium/convert/html`. The API image has no Chromium dependency. Response body is the PDF binary, used in-memory and attached to Nodemailer. The source data (`tailoredCvSnapshot`, `coverLetterText`) in `JobApplication` is the persistent record.

**Alternative considered:** Puppeteer in-process — rejected; bundles Chromium inside the API image (large, complex Dockerfile) and ties PDF rendering to the API process lifecycle.

### Auth: multi-user email+password with bcrypt
Users register with email + password; passwords hashed with `bcrypt`. JWT payload includes `sub: userId`. All resource queries filter by `userId` extracted from the JWT via a `@CurrentUser()` decorator. `REGISTRATION_ENABLED` env flag (default `true`) disables registration without code changes.

### Email: Daily digest via cron
A NestJS `@Cron` in `NotificationModule` runs on a configurable schedule (default `0 8 * * *`). It queries `JobApplication` records where `matched = true` and `emailedAt IS NULL`, generates PDFs for each, bundles into one email, and sets `emailedAt` for all.

### Frontend: Nuxt 3 with `useFetch` + JWT cookie
JWT stored in an httpOnly cookie. Nuxt middleware redirects unauthenticated users to `/login`. API calls use `useFetch` with a base URL from runtime config. No SSR for authenticated pages (client-only rendering after hydration check).

### Shared types: `packages/shared` as local workspace package
Named `@job-seeker/shared`. Exports TypeScript interfaces for all entities and queue payloads. Both `apps/api` and `apps/web` declare it as a workspace dependency.

## Risks / Trade-offs

- **Gotenberg cold-start latency** — first PDF request may be slow while Chromium initialises inside Gotenberg. Mitigation: Gotenberg keeps a warm browser pool; acceptable for a background queue processor.
- **`@klerick/nestjs-json-api` maturity** — less battle-tested than manual JSON:API. Risk: missing features or breaking changes. Mitigation: pin to a specific version; plain REST fallback for any gaps.
- **LLM latency in queue** — Claude Haiku is fast but external. Risk: queue backlog during bursts. Mitigation: Bull concurrency config per processor; matching and generation processors run with concurrency 2.
- **MikroORM migration drift** — if entities change post-scaffold, migrations must be kept in sync. Mitigation: always generate migrations from entity schema changes, never edit entities without a migration.

## Migration Plan

Greenfield — no migration needed. Steps to bring up local dev:
1. `yarn install`
2. `docker compose up -d postgres redis gotenberg`
3. `yarn workspace @job-seeker/api mikro-orm migration:up`
4. `yarn workspace @job-seeker/api seed` (loads JobSourcePreset seed data)
5. `docker compose up`
